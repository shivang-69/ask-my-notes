Retrieval-augmented generation (RAG) is a technique that enhances the capabilities of large language models (LLMs) by integrating external knowledge sources. By retrieving relevant documents or information from a database, RAG allows the model to generate more accurate, contextually relevant, and up-to-date responses. This is especially useful for tasks that require specific domain knowledge or access to private data. RAG systems typically consist of a retrieval component, which searches a document collection, and a generation component, which uses the retrieved documents to produce the final answer. In this project, we are building a simple RAG pipeline, starting with document chunking.

This is paragraph 2. Document chunking is the process of breaking down large text documents into smaller, manageable pieces or "chunks." This is a crucial step in RAG pipelines because LLMs have a limit on the amount of text they can process at once, known as the context window. Furthermore, chunking helps in retrieving only the most relevant sections of a document, reducing noise and improving retrieval precision. If we retrieve entire documents, we might exceed the model's token limit or dilute the context. Therefore, finding the right chunking strategy—balancing chunk size and overlap—is key to the performance of the RAG system.

This is paragraph 3. There are several chunking strategies, ranging from simple character-based or word-based splitting to more advanced semantic-based splitting. In this step of the project, we are implementing a simple word-based chunking approach with overlap. This means we will split the text into chunks of a fixed number of words (around 500 words), with a certain number of words overlapping between consecutive chunks. The overlap ensures that context is not lost at the boundaries of the chunks. For example, if a sentence is split in half across two chunks, the overlap helps maintain the semantic link between them, allowing the model to understand the full context.

This is paragraph 4. To implement the word-based chunking logic, we first need to read the content of the documents. Our script will support both plain text files (.txt) and PDF documents (.pdf). For text files, we can easily read the content using Python's built-in file handling. For PDF files, we will use the pypdf library to extract text page by page. Once we have the full text of a document, we can tokenize it by splitting the text on whitespace. This gives us a list of all the words in the document. We then iterate through this list to create our overlapping chunks.

This is paragraph 5. Let's discuss the chunking algorithm in detail. Suppose we have a list of words of length N, and we want to create chunks of size C (e.g., 500 words) with an overlap of O (e.g., 50 words). The first chunk will contain words from index 0 to C. The second chunk will start at index C - O and contain words up to (C - O) + C. The third chunk will start at index 2 * (C - O) and contain C words, and so on. We continue this process until we reach the end of the word list. The last chunk might be smaller than C words, but it will contain all the remaining words in the document.

This is paragraph 6. Choosing the right chunk size and overlap is an empirical decision that depends on the specific use case and the model being used. A larger chunk size (e.g., 1000 words) can capture more context but might introduce irrelevant information and increase the computational cost. A smaller chunk size (e.g., 100 words) is more precise but might split important context across multiple chunks. Similarly, the overlap should be large enough to preserve context but not so large that it creates redundant chunks. A common starting point is a chunk size of 500 words with an overlap of 50 to 100 words.

This is paragraph 7. In a full RAG system, after chunking the documents, the next step is to generate vector embeddings for each chunk. An embedding is a numerical representation of the semantic meaning of the text, typically represented as a high-dimensional vector. We use an embedding model to convert each chunk into a vector and store these vectors in a vector database. When a user submits a query, we generate an embedding for the query and search the vector database for the chunks whose embeddings are most similar to the query embedding.

This is paragraph 8. The retrieval step typically uses a similarity metric like cosine similarity to find the top-K most similar chunks. Once the relevant chunks are retrieved, they are formatted into a prompt along with the user's query and sent to the LLM. The LLM then uses this context to generate a response. This process ensures that the model's response is grounded in the retrieved information, reducing the likelihood of hallucinations and improving the accuracy of the answer. RAG has become a standard architecture for building question-answering systems over custom datasets.

This is paragraph 9. There are many open-source libraries and frameworks that simplify the process of building RAG applications, such as LangChain and LlamaIndex. These frameworks provide pre-built components for document loading, chunking, embedding, vector storage, and query execution. While these libraries are very powerful, building a RAG pipeline from scratch—as we are doing here—helps in understanding the underlying concepts and design trade-offs. It gives us full control over each step of the pipeline and allows us to customize the behavior to our specific needs.
